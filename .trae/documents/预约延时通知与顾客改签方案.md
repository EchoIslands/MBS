# 预约延时通知与顾客改签方案（v1 / v2）

## Context（背景与目标）

顾客按预约时间到店接受服务时，临时增项需要延长服务时长（延时）。若延时导致该发型师后续预约被顶到，发型师需要一键识别「受影响」顾客并发起通知，让被影响顾客二选一：换空闲发型师 / 改时间段。

现状约束（已确认）：
- 系统**无实时排班表**，「空闲发型师」只能靠 `bookings` 表预约占用 + `shop.employees` 角色动态反推，缺乏班次/上班时间依据，做可靠的空闲列表不现实。
- 已有「换发型师」「改时间」能力，但仅限店铺端权限；顾客端只能「取消/评价」，且无「延时」临时调整概念。

## 已确认决策（用户拍板）

1. **通知**：v1 做站内「我的预约」警示；**微信订阅消息列为 v2 第 1 顺位必做项**（模板申请 + 后端发送）。纯站内提示不作为长期方案。
2. **换发型师**：因无实时排班，**v1 不做顾客自助「换空闲发型师」**；换发型师放 v2（需先确定空闲数据源）或 v1 走客服人工确认（用店铺端现有换发型师能力）。
3. **顾客不处理**：`delay_state` 增加 `no_response` 状态；**超时 4 小时**无响应 → 标记 `no_response` 并保留原预约（不自动取消），店铺端人工跟进。

## 数据模型（迁移 `024_booking_delay.sql`）

`bookings` 表新增 4 个可空列：

```sql
ALTER TABLE bookings ADD COLUMN IF NOT EXISTS delay_state TEXT;
ALTER TABLE bookings ADD COLUMN IF NOT EXISTS delay_reason TEXT;
ALTER TABLE bookings ADD COLUMN IF NOT EXISTS delay_expected_end TIMESTAMPTZ;
ALTER TABLE bookings ADD COLUMN IF NOT EXISTS delay_created_at TIMESTAMPTZ;
```

- `delay_state`：`null` 正常 / `needs_action` 待处理 / `no_response` 超时未响应 / `rescheduled` 已改时间 /（`reassigned` 预留 v2）
- `delay_reason`：通知文案（如「发型师临时延时约 30 分钟」）
- `delay_expected_end`：延时后预计结束时间
- `delay_created_at`：标记 needs_action 的时间（用于超时判定）

## v1 开发任务清单

### 1. 数据库迁移
- 新建 `migrations/024_booking_delay.sql`（上述 4 列）。

### 2. 类型定义
- `shared/types.ts`：`Booking` 增加 `delayState?` / `delayReason?` / `delayExpectedEnd?` / `delayCreatedAt?`；新增 `DelayState` 类型。

### 3. 后端 `api/routes/index.ts`
- `bookingFromDb`（L723）增加 delay 字段 snake→camel 映射。
- 新增 `POST /bookings/:id/delay`（auth，权限 `ceo`/`shop_manager`/`customer_service`/该发型师本人）：
  - body `{ extraMinutes, reason? }`
  - 取原预约，`expectedEnd` = (`scheduled_end_time` 或 `scheduled_time+60min`) + extraMinutes
  - 更新本预约 `scheduled_end_time = expectedEnd`
  - 查受影响：同 `stylist_id`、`status in (pending,confirmed)`、`scheduled_time >= 原scheduled_time` 且 `< expectedEnd`、`id != 本预约`
  - 受影响预约批量写入 `delay_state='needs_action'`、`delay_reason`、`delay_expected_end`、`delay_created_at=now`
  - 返回受影响列表（供店铺端提示数量）
- 新增 `PUT /bookings/:id/delay-respond`（顾客自助，无 auth，仿 `/cancel` 用 `customerId` 校验）：
  - v1 仅支持 `action:'reschedule'`，body `{ customerId, action, scheduledTime }`
  - 校验 `customer_id === customerId` 且 `delay_state === 'needs_action'`
  - 复用 `/schedule` 的结束时间推算（L1338-1350）与冲突检查（L1352-1377）
  - 写 `scheduled_time/scheduled_end_time`，`delay_state='rescheduled'`，返回更新 booking
- **超时惰性过期**：在 `GET /bookings`（店铺）与 `GET /bookings/customer/:customerId`（顾客）读取前，先执行一次 `UPDATE bookings SET delay_state='no_response' WHERE delay_state='needs_action' AND delay_created_at < now() - interval '4 hours'`，使 no_response 状态自动落地（服务端无常驻进程，用读取时惰性 GC 代替定时任务）。

### 4. 前端 API 封装 `src/api.ts`
- `bookingApi` 新增 `delayBooking(id, extraMinutes, reason?)`、`respondDelay(id, payload)`。
- `getCustomerBookings` / 店铺列表返回已含 delay 字段（经 bookingFromDb 透传）。

### 5. 店铺端 `src/pages/shop/BookingManagement.tsx`
- 预约行/详情弹窗对「已确认/进行中」预约加「延时」按钮 → 弹窗输入延时分钟数 → 调 `delayBooking` → 提示「已通知 N 位受影响顾客」并刷新。
- 「延时」详情弹窗展示受影响顾客列表及其状态（`needs_action` / `no_response` / `rescheduled`），no_response 项可人工跟进（复用现有换发型师/改时间按钮）。

### 6. 顾客端 H5 `src/pages/customer/Profile.tsx`
- 「我的预约」列表：`delayState==='needs_action'` 显示警示横幅「发型师临时延时，请选择处理方式」+ 两个按钮：
  - **改时间** → 日期/时间选择弹窗 → `respondDelay(action:'reschedule')`
  - **联系门店** → 点击显示门店电话（复用现有店铺查询接口 `GET /shops/:id` 取 `phone`）
- `delayState==='no_response'` 显示「预约已超时未处理，请联系门店」。
- 处理后刷新列表。

### 7. 小程序 `mini-program`
- `mini-program/api/booking.js` 新增 `delayBooking` / `respondDelay` 封装。
- `pages/profile` 「我的预约」列表：同步 H5 的 needs_action 警示 + 「改时间」自助 + 「联系门店」（通过 `wx.makePhoneCall` 拨打门店电话），文案与 H5 一致。

### 8. 文档更新
- `MBS 项目开发宪章.md`、`项目状态日志.md`：记录本功能、024 迁移与经验教训。

### 验证
1. `npm run build` 无 TS 错误。
2. Supabase SQL Editor 执行 `024_booking_delay.sql`。
3. 端到端：店铺端点「延时」→ 后续预约变 `needs_action` → H5/小程序「我的预约」出现警示 → 「改时间」成功冲突检查通过、`delayState='rescheduled'`；超时后变 `no_response`。
4. 回归：普通预约展示/取消/评价不受影响。
