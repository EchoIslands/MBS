# 财务报表支付时间统一整改

## 证据与计划

财务接口按结算创建时间截取本年数据，页面又独立按创建时间计算趋势、增长、明细。跨年旧单新付可能完全漏统计；客单价卡片以订单数为分母，增长却以服务数为分母；Excel 只有汇总和预约，没有实际收款明细。

1. 统一北京时间和金额计算。微信仅采用已核实的 `wechat_success_time`，关联支付状态、金额、交易号或多笔记录异常时列为待核对。无可信时间的历史款保留展示，不猜日期、不计入按日/月统计。
2. 现金、银行卡、支付宝、余额等尚未保存独立可信支付时间，继续沿用已完成结算的创建登记时间，并醒目标注局限；不将其伪称实际支付时间。余额消费不等于新增入账，报表不等于银行卡到账净额。不改变定价、折扣、提现费率或权限。
3. 服务端分页读取本店已完成结算和关联明细，不以创建年份截断；支付查询失败不能返回看似完整的零金额。提供同一份快照用于卡片、图表、增长、搜索明细和导出。
4. 明细分别显示金额、创建时间、实际微信支付时间、统计依据；Excel 增加结算明细，保留既有预约附表并明确标为“非收款”，不计入财务汇总。客单价统一为结算金额/订单数；设计师榜单和导出均明确本月。
5. 合成测试覆盖跨年旧单新付、北京时间边界、未来时间、缺时间/金额不符/多笔异常、跨店隔离、超过1000行与查询失败；再做类型、构建、隔离页面验收。

## 范围与发布边界

本批仅财务报表，不声称老板视图、首页、发型师看板等其他统计已全部统一。无需新增数据库迁移；复用前批037可信支付时间字段及038活动商户订单映射，换码后的商户号也必须准确显示。037/038发布前按各自说明升级。本地验证，不提交、不推送、不连接生产补数据、不操作真实交易。

## 验证结果

- 新增4项纯逻辑测试及1项HTTP综合回归：跨年旧单新付、北京时间跨日/跨年、零元订单、按分累加、客单价分母、商品不算服务次数；旧时间缺失、未来时间、交易号缺失、金额不符、多支付映射均不计入日期统计。
- HTTP合成库验证本店隔离、1003条结算完整返回、单单1004条旧表项目完整统计、活动商户号与账务支付ID区分、支付查询失败503不返回部分汇总。财务仍由原`financial:read`权限链保护，未扩大岗位权限。
- 浏览器在隔离API验证：33.64合成旧单显示8月创建、10月22日微信成功；按成功时间排序，月份趋势归十月；23.55合成缺时间单单独提示、筛选可见。此处日期/金额为合成数据，不是补查到真实33.64付款时间。
- 实际点击导出并读取xlsx内容：财务汇总、结算收款明细、预约参考（非收款）三张表；包含全部3条合成结算及创建/发起/实际付款时间、统计口径、交易号，缺时间款明确未计入。搜索33.64只显示对应合成单；搜索不截断导出。
- 切换趋势关闭旧曲线插值动画，防止短暂显示旧范围曲线。390px页面无整体横向溢出，宽表内部横向滚动。请求503显示明确错误、撤去旧汇总并禁用导出，刷新后恢复；最终页面无运行错误。截图：`financial-report-ui-2026-10-23.jpg`。
- 最终构建、全量回归及后端健康检查结果由状态日志记录。未提交/push，未安装生产迁移，未修改生产订单或密码；私有使用说明另存仓库外，不加入部署产物。

## 局限与下一步

- 一个响应内复用同一组记录和截止时间，解决前端三次请求/独立时钟的口径不一致；不是数据库多表事务快照，采集期间有新付款时需再次刷新。
- 财务日期统计缺失的历史款由提示公开数量与金额，不能用创建时间冒充真实微信时间。现金等独立确认时间尚未持久化，仍按登记时间，后续另做迁移；暂未做退款净额、储值流入/消费和提现净额的全账本对账。
- 每500行/每100个ID分页防止数据库默认行上限漏单；当前仍汇集全历史完成单，规模持续增长后应另做数据库聚合和服务端分页导出，不宣称无限规模性能已验收。
- 下一批检查首页、老板视图、发型师统计的日期来源，逐项统一可信支付时间；不改变设计师提成、价格和经营政策。正式支付、退款、迁移及上线仍须按既有发布清单独立验收。
