# 微信订单管理接入评估与本批计划

## 核查结论

- 主人随后进入“订单信息录入”，同意接入“订单与卡包”并回传登记表。表单明确 Path 必须包含 `${商品订单号}`，微信替换为支付预下单接口中的 `out_trade_no`，最多登记一条；占位符语义已确认。
- JSAPI 是支付前下单接口，description 必须在下单请求中填写真实商品信息。不能在付款成功后再次调用 JSAPI 来“同步”，以免另建支付。
- 项目现有微信收款为门店 Native 扫码；小程序商品购买支持余额/到店付款，尚无 JSAPI、wx.login 换取本小程序 OpenID 的链路。不得假称这些已接入。
- 发货信息同步是另一组 API，要求本小程序下的付款人 OpenID、微信支付订单及真实交付信息。付款成功不能当作已发货、自提或服务完成。不得把储值消费当作微信支付订单上传。

## 本批范围及验收标准

1. 微信新建 Native 支付请求的 description 使用服务端原结算项目快照中的名称与数量，限制到微信长度范围；只读原快照，不按当前价格重算。已持久化的请求恢复保持原 description 和原商户单号，不变更既有请求。
2. 增加独立小程序“微信订单详情”页面，通过微信商户支付单号定位原结算。服务端校验顾客本人凭证、同店和归属；不能凭单号查他人订单，不返回密码、手机号、OpenID、员工资料或网关请求。
3. 深链经过未登录、凭证失效、强制改密后返回原单；参数严格限制为微信商户单号。保留创建时间与经微信核实的实际成功时间，错误可重试，不能显示假成功。
4. 本地合成 HTTP/小程序 Page 回归及构建、API 健康检查。测试不连接生产或真实微信，不产生支付/发货动作。不新增 SQL、不修改经营与价格，不代提交推送。

## 后续接入与登记限制

- 本批不是新增小程序微信支付。没有本小程序 OpenID 和真正微信支付的商品订单，不做空壳发货上传，也不向平台申报“已全部接入”。
- 已确认登记格式为 `pages/payment-order/payment-order?outTradeNo=${商品订单号}`；保留中文占位符及 `${}` 原样，其中微信替换的值为 out_trade_no，不能手工替换成结算单号或 PO 商品展示编号。下拉框如需选页，选择 `pages/payment-order/payment-order`，右侧完整 Path 保留查询参数。正式录入须等后端和含此页面的小程序发布验证完成。
- 该入口本批只覆盖现有微信结算支付。日后小程序商品接 JSAPI 时，需要增加商品支付映射、微信身份及真实发货/自提同步，验收后才能宣称覆盖商品微信支付。
- 页面与后端必须分别发布，再通过体验版以本人订单验证入口。只 push 后端不能让已上传 1.1.0 出现新页面，切勿提前把尚未发布的 Path 当成接入成功。

- 已实现原单项目 description、本人微信结算查询 DTO 与路由、小程序微信订单详情页、未登录/401/强制改密后返回原单；原请求快照重试不改 description、金额或商户单号。
- 四文件联合回归 62/62 通过，无失败或跳过。包括隔离 PGlite 原子支付/恢复、真实 HTTP 权限与回调、实际 Page 登录深链及异步会话保护；全为合成数据，不连接真实微信或生产库。
- `npm run build`（类型检查及 Vite）通过；`git diff --check` 通过，仅已有 LF/CRLF 提示。使用真实 backend/app 的本地合成配置与外网阻断，浏览器操作确认健康接口 200、本人订单 200/no-store、无凭证 401、不存在订单 404/no-store。
- 微信开发者工具 3.0.2 已完成新页面原生编译及渲染：无效链接显示错误和重试、合成已付订单显示 33.64、项目明细、三个编号及北京时间创建/支付时间。原生检查发现并修复六处 WXML 条件未绑定、页面被未使用文件过滤漏掉的问题；project.config.json 显式 include 页面目录，在原有过滤开启时完整编译成功。开发工具的两条预加载提示仍存在，无页面 JS 错误。临时编译模式已移除，安全配置未放宽。

- 本轮无新 SQL、生产读写、真实支付/退款或发货上报，不代提交/推送、上传或登记 Path。JSAPI 商品支付及自动发货上报尚未实现，不能据此宣称平台全部接入完成。
