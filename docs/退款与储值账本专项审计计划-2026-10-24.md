# 退款与储值账本专项审计计划（2026-10-24）

## 目标

只基于代码与隔离测试，核对顾客储值余额、推荐/本金拆分、服务退款和商品退款的每个写入入口是否原子、可追溯且能重复安全调用；确认页面和报表没有把“退款申请/审批”误表示为退款到账或净收入。

## 范围与边界

- 盘点客户余额、储值交易流水、服务退款、商品退款、余额消费和财务统计的后端入口、RPC、触发器、页面与测试。
- 检查同一事务中的客户余额、流水、订单/退款状态、商品库存变化；检查并发、重试、重复申请、权限和跨店隔离。
- 检查是否存在绕过原子 RPC 的直接余额写入，以及当前流水字段能否支持逐笔对账。
- 不连接生产数据库，不读取或更改生产记录，不执行真实退款或支付。
- 不决定退款退回原渠道/余额/银行卡的经营政策，不改变储值本金/赠送金/推荐金的抵扣顺序，不调整退款金额或财务报表“净收入”口径；发现这些规则缺口时列出证据并等待店主决定。

## 执行顺序

1. 画出各余额写入/退款状态转换的数据流，记录文件、函数、表和字段。
2. 用迁移与代码相互校对，标出原子边界、幂等键、金额来源、权限检查和流水生成条件。
3. 对每个可由现有约定判定的安全不变量编写或运行隔离回归测试；不把模拟测试描述成生产验收。
4. 将发现分为明确缺陷、已知业务规则待定、数据结构无法证明三类。只有明确违反现有安全不变量且无需经营决策的缺陷进入修复。
5. 若修改代码，先补测试，再执行 `npm run build`、相关全量测试、`git diff --check`、本地 API 健康检查，并记录限制及待用户手测事项。

## 验收标准

- 每条客户余额增减都能定位到唯一的受控写入入口，或者明确列出未纳管入口与影响。
- 已完成的余额支付/商品退款不能重复扣/退；余额、交易流水和业务状态在事务中一致提交或全部回滚。
- 服务退款“申请/审批/完成”的界面与接口语义可解释；不把审批完成推断为资金到账。
- 明确指出历史数据是否足以做余额全账本重算；缺少流水或历史基数时不得伪造对账结论。
- 不变更门店定价、会员赠送、退款渠道与财务口径。
