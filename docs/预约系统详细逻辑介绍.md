# 预约系统详细逻辑介绍

> 核对日期：2026-11-12。本文件说明当前仓库的预约与现场排队实现，供门店、产品和开发接手使用；它不是线上功能已验收的证明。项目负责人反馈生产库 046、047、048、049 已执行成功，数据库版本尚未由维护者独立只读核验，配套后端、H5 与小程序版本仍待逐端确认。具体发布状态以[当前工作现场](current-state.md)为准。

## 一、先分清三种时间与两类状态

- **预约时段**：顾客选择的是到店时间段，页面按半小时展示，不承诺到点立刻开剪。半小时也用于同店时段队号分组，不等于所有服务都只用30分钟。
- **服务参考时长**：由门店服务目录给出，创建预约时保存一份用于现场估计；实际操作可能更快或更慢，不能以倒计时自动完成服务。
- **现场等待范围**：顾客到店并由前台确认后，按该发型师当前服务、前方人数及历史实际时长动态计算，属于沟通参考，不用于决定排队先后。
- **预约业务状态**：待确认、已确认、已完成、已取消分别记录在预约状态字段。门店采用自动确认或人工确认，由门店设置决定。
- **现场排队状态**：待到店、已到店、暂离、已确认返回、已叫号、过号、服务中、服务结束等另行记录。预约确认、现场服务结束、财务结算是不同事件，不能互相代替。

## 二、顾客怎样预约

1. 顾客在小程序或 H5 选择门店、服务、日期、半小时时段，可选指定发型师或智能匹配；没有登录时先完成顾客登录。小程序当前展示未来7天；时段依据门店营业配置生成，今天只展示当前时间之后的时段。缺少营业配置时客户端回退为09:00—20:30的开始时段。
2. 前端按所选服务参考时长检查发型师现有待确认/已确认预约是否重叠；需要金牌或店长资质的服务只展示符合资格的发型师。智能匹配从有资格且当前不冲突的人中，选当天有效预约数较少者。这个预约数仅用于排序，**不是等待分钟数**。
3. 顾客确认后，服务端重新读取本店顾客、有效服务、在职发型师、服务资质、门店营业时间及确认方式；姓名、服务名称、价格等以服务端目录为准，不信任客户端显示值。
4. 数据库按服务参考时长检查同一发型师的有效预约重叠，并对门店预约写入串行化；被他人抢占的时段应返回冲突提示，顾客刷新后改选。半小时队号按同门店、同日期时段及有效预约分组，不代表现场开始服务的最终顺序。
5. 创建成功后按门店配置进入“待门店确认”或“已确认”，顾客端进入对应预约的排队页。网络失败或结果不确定时先查看“我的预约”，避免重复提交。

以上对应[顾客 H5 预约页](../src/pages/customer/Booking.tsx)、[小程序预约页](../mini-program/pages/booking/booking.js)、[预约路由](../backend/routes/index.ts)和[档期冲突迁移](../migrations/031_booking_checkout_consistency.sql)。客户端可用性只是预检查，最终以服务端及数据库写入结果为准。

## 三、到店后的现场规则

| 环节 | 顾客看到或执行 | 门店/发型师执行与约束 |
| --- | --- | --- |
| 到店 | 查看预约及联系门店入口 | 前台确认本人到店后才进入该发型师现场队列；未来预约和未到店不计算现场等候人数 |
| 暂离 | 登记预计离开10或20分钟 | 暂离者不占“可立即服务”的位置；返回后按规则恢复，不打断正在服务的顾客 |
| 返回 | 点击“我已返回” | 仅形成待核实请求；前台确认本人在场才恢复队列，不能远程直接插队 |
| 准备与叫号 | 查看准备返回提示、正式叫号，点击“我已看到” | 准备提醒不开始过号计时；正式叫号起有10分钟宽限。看到确认不等于人在服务位；未确认时前台联系顾客 |
| 过号 | 返回后联系前台 | 宽限结束由前台确认，不自动跳号。首次过号且60分钟内返回保留原优先级；再次过号或超60分钟按返回时间重新排 |
| 服务 | 查看最新状态和等待范围 | 同一发型师不能同时开两单；暂停接客期间不能新开单。发型师更新剩余10/20/30分钟，结束必须人工确认 |
| 异常 | 可一键求助或拨打门店电话 | 等待超过45分钟突出提醒；调整顺序、跳过前方顾客开单须填写原因并留痕。取消、改期、换人、退款仍走各自业务入口 |

排队按预约当天和指定发型师处理；现场操作由后端事务核对角色、门店、当前状态与快照版本。多人同时操作同一单时，旧版本被拒绝并要求刷新；事件及联系记录保留供复盘。顾客只能查本人，发型师只处理本人预约，前台/客服及管理者按门店角色操作。细节与完整验收见[实时排队规则](live-queue.md)、[排队服务](../backend/services/liveQueue.ts)及[048 迁移](../migrations/048_live_queue.sql)。

## 四、等待时间怎样估算与同步

- 同一发型师、同类服务的近90天有效实际服务时长，过滤短于5分钟及超过480分钟的记录；至少8个样本时，用中位数到85分位给出范围。样本不足时用服务参考时长约0.75—1.5倍，并标明是参考值。
- 前面每位现场等候顾客分别累计区间；正在服务的顾客优先用员工最近更新的剩余时间。进度超15分钟未更新或预计已耗尽时扩大不确定性，不自动判定完工。发型师暂停接客时纳入预计恢复时间。
- 页面可见时约每5秒取一次服务器快照，操作完成、回前台或网络恢复时立即刷新，并显示最后成功同步时间；超过20秒未成功同步或读取出错，停止业务操作，旧画面不可当作现场顺序。5秒是轮询频率，**不是端到端通知送达承诺**。
- 锁屏、离开小程序、微信后台或关闭 H5 时，不保证轮询、振动或提示音到达。当前没有排队专用短信或微信订阅通知，前台须用电话兜底；登录验证码模板不能用作叫号通知。每日单店快照达到500条预约时会明确报错，不截断后假装完整。

估算计算见[共享逻辑](../shared/lib/liveQueue.ts)；三端实际操作与断网验收见[实时排队规则](live-queue.md)。

## 五、变更、延时与结算边界

- 门店客服、店长、CEO及对应发型师可按权限修改预约时间；修改时保留原服务时长或使用明确的自定义结束时间，并检查与同发型师其他预约是否冲突。顾客自主取消须本人会话与预约归属核验；员工取消、调配发型师及服务完成也各有权限限制。
- 发型师临时延时的旧预约流程会标记受影响的后续预约“待处理”，顾客处理入口目前只支持改时间；它与新现场排队的准备提醒/正式叫号不是同一个通知渠道。不能假设顾客锁屏时会及时看到变化。
- 发型师确认服务结束不等于收款。只有正式结算事务才处理余额、次卡、权益、消费统计和流水，避免服务完成和结算各计一次。详情见[预约到结算整改记录](预约到结算流程整改-2026-10-22.md)。

## 六、已知边界与上线验收

目前按门店设置校验**预约开始时间**是否营业；未据此承诺一项较长服务一定在关门前完成。客户端只展示近7天且按当天已过时段过滤；未来更长预约窗口、临时停业、跨日服务和自动改派不属于这次现场排队逻辑。历史预约缺少参考时长时以保守默认值估计，不能伪造已发生的到店或服务记录。

生产库 048、049 执行成功依据项目负责人反馈，**不代表配套代码已经推送或生效**。上线前核对数据库结构与函数权限、Vercel 后端及 H5 的部署版本、小程序体验版/正式版；用顾客、发型师、前台三种身份和两台设备演练新建预约、时段冲突、暂离返回、叫号过号、服务超时、断网恢复及结算分界。通知渠道未建成前，必须保留人工电话流程，不能向顾客承诺离店后自动实时获知叫号。
