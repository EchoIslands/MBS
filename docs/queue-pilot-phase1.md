# 排队试运行第一阶段：数据采集与前台快记

> 历史阶段说明：2026-11-12 主人已确认生产046、047执行。顾客展示、动态估时与三端操作已扩展为[实时排队方案](live-queue.md)，本页保留原采集口径；下述“第一阶段不改变顾客展示”等边界仅描述旧阶段。新增048尚未生产执行，新增代码未部署。

## 目标与已定规则

收集两周的预约、到店、暂时离店、叫号、过号、实际服务开始和结束时间，为下一阶段按发型师与服务估计时长提供数据。门店确认：建议提前 10 分钟到店；叫号后 10 分钟宽限；过号保留记录，顾客返回后安排下一个可用空档。第一阶段不自动过号、不自动改期，也不改变现有顾客排队展示和结算。

## 本地实现的位置

- `migrations/046_booking_queue_pilot.sql`：在预约主表追加状态和时间快照，新增 `booking_queue_events`；`occurred_at` 是事件发生时间，`recorded_at` 是录入时间。新预约保存 `planned_duration_minutes` 和来源快照，旧预约不回填。
- `backend/routes/index.ts`：员工记录事件、查询本店事件；店长当天更正时间由服务端校验权限。数据库函数在同一事务内更新快照并追加事件；更正保留原事件，另记关联的更正事件。
- `src/pages/shop/QueueQuickDesk.tsx`、`src/App.tsx`：门店 H5 的“今日到店快记”，大按钮记录当前时间，店长按权限更正当天时间。返回、过号是必要的辅助状态；完成服务不代表收银结算完成。
- `tests/booking-queue-pilot.test.ts`：隔离数据库里的事件/快照事务测试，不能代替真实 HTTP、权限和店面试运行。

## 采集口径与阶段边界

- 只把现场动作的实际时间记为事实：按钮默认当前时间；漏点后由有权限人员在当天更正 `occurred_at`，原始记录时间 `recorded_at` 和更正关系保留。未操作的离店、叫号、开始或结束不得凭预约时间推算补齐。
- 试运行拟收集两周数据是本店本阶段的安排，不代表数据已积累或未来算法已训练。按发型师 × 服务分析时先检查每类有效样本量、缺点/更正比例、异常尾值和跨日情况；样本不足只报告分布与不确定性，不直接生成承诺到分钟的预计开始时间。
- 前台只见本店授权预约；导出或分享统计时去标识顾客信息。若操作负担、漏点或更正比例使数据无法解释，应先改进记录流程，停止基于该样本推出自动排班规则。是否进入第二阶段由门店确认，顾客端展示不能先于真实现场验收。

## 上线前验收

1. 只读核对目标数据库现有预约字段和 046 前置依赖，在独立测试库运行 046，并检查重跑及旧预约数据；不能把本地文件存在视为生产已迁移。
2. 使用不同员工角色和不同门店通过真实 HTTP 操作到店、离店、返回、叫号、开始/完成、过号与当天更正，验证非法状态、跨店及越权均被拒绝。
3. 核对每次动作的两种时间、操作者与事件顺序；更正不覆盖原事件，预约快照与事件一致；检查日期边界和忙时误触。
4. 由项目负责人确认回滚与数据保存方案后再发布。两周采集期间记录缺点/漏点率、服务时长分布与异常案例；第二阶段前台完善及小程序排队展示基于这些数据另行设计和验收。顾客扫码自动到店尚未开放，须先设计防远程代扫机制。
