## 本批差异

- migrations/029_customer_password_change_required.sql：新增 is_weak_password、password_reset_at；初始化执行记录表开启 RLS 且撤销匿名/登录角色权限；数据库余额付款在锁定客户行后同时检查身份核实和改密标记。
- scripts/sql/initialize_legacy_customer_passwords_once.sql：仅处理 NULL/去空白后为空的 password_hash，逐条调用 pgcrypto crypt+gen_salt(bf,12) 生成独立 bcrypt 盐；设置改密标记、清除旧身份核实员工/时间。非空已有哈希完全不覆盖，包括已经自设 123456 的历史记录，本批不自动扫描/替换这些密码。
- 脚本以固定 run_key 记录一次执行；密码更新和执行记录同事务。失败整体回滚。再次执行直接跳过，连后来新增的空密码客户也不会被重置。只输出影响数量和执行时间，不输出手机号或哈希。
- api/middleware/permissions.ts、api/lib/tokens.ts：JWT 携带改密声明，每次本人接口仍以数据库现值为准；受限顾客只能恢复最小会话信息、本人改密、退出。登录/恢复响应不带余额、订单、资料，业务 API 返回 403 PASSWORD_CHANGE_REQUIRED。
- api/routes/index.ts：新增 POST /api/customers/:id/password/change。本人凭证+正确原密码+六位新密码+确认一致；禁止新密码为 123456 或与原密码相同。沿用数据库全局 IP 限流。按旧哈希条件更新防并发覆盖；改密不写 identity_verified 等核实字段；新哈希使旧 token 失效，签发新 Cookie/小程序 token。当前错误原密码返回 400，不清掉仍需改密的会话。
- api/utils/case.ts：客户管理等通用响应转换过滤 password_hash/passwordHash，避免新增初始化后员工列表携带哈希。
- mini-program：新增 change-password 独立页面，登录页/登录弹窗/恢复会话统一进入；缓存 Token 与改密标记；Page 生命周期统一拦截深链、返回和 tab 切换；403 也会重新进入改密界面。标记只用于体验，不能取代服务端校验。支持退出登录重新认证。
- H5：新增 ChangePassword 页面、客户路由守卫与本人改密调用，与小程序保持六位密码校验和文案一致。
- 员工“确认顾客本人”入口沿用上一批：本人改密不代表核实，核实不代表已改密，两道条件各自生效。员工现场结算的原有流程保留。

## 门店告知与验收

仅对本轮初始化客户告知“初始密码 123456，首次登录请先修改”。忘记新密码时继续联系门店；后台既有单客重置仍为手机号后六位，不在本批改成统一密码。

顾客改密后可查看本人资料；线上余额付款仍提示“首次使用需由门店核实身份”。店员在客户详情核对本人后点“确认顾客本人”，刷新后才允许线上付款。不得因为使用了统一初始密码就视为身份已核实。
