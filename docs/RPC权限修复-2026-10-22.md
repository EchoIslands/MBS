# RPC 执行权限修复计划

用户只读检查发现 10 个函数对 anon/authenticated 均可执行。旧 026–029 只 REVOKE FROM PUBLIC，未撤销角色直接授权；隔离测试没有模拟托管数据库默认角色授权，因而漏检。此结果不证明已发生越权或资金损失，不对生产发起漏洞探测。

新增 030 迁移，只修改这 10 个精确签名的执行权限：撤销 PUBLIC、anon、authenticated，保留 service_role；同事务核验有效权限，若继承授权仍导致可执行则整笔失败，不改角色成员关系或全库默认权限。不修改客户、密码、余额、函数体或业务状态。已有数据库提供独立 pg 执行脚本，不重跑历史建库/密码初始化；完整 setup 也包含 030，避免新环境再次遗漏。

验收：模拟 Supabase 默认授权后能复现 20 条问题；执行 030 后只读检查通过；匿名实际执行被数据库拒绝，service_role 权限保留，重复运行不改业务数据；缺函数导致事务回滚。本轮仅隔离验证，由用户手动执行生产修复。

## 执行步骤

现有数据库已完成结构与密码初始化，不重跑 setup 或 init-legacy-passwords。PowerShell 在项目根目录依次执行，第一条失败停止：

```powershell
Set-Location 'E:\01Programe\01MBS\MBS'
npx tsx scripts/fix-rpc-permissions.ts
```

看到 `[完成] 030 权限事务已提交` 后执行：

```powershell
npx tsx scripts/verify-release.ts
```

完成标志为 passed:true、issues:[]、checkedFunctions:10。当前用户结果为 total=443、empty_password=0、whitespace_password=0、must_change_password=442、unverified=443；修复不改变这些状态。并发正常业务可能改变数量，不能把合理变动视为脚本改密。

脚本通过 pg 仅执行 migrations/030_restrict_sensitive_rpc_execution.sql，不重建函数、不重置密码、不扣款。锁等待 15 秒、语句 30 秒，授权和有效权限检查同事务。若遇继承授权导致有效权限仍存在，事务失败并回滚，不能靠放宽验收恢复；需要进一步只读核对角色关系。若断线而无法确认提交，以 verify-release 结果为准。

新环境的 setup-db.ts 已同步执行 025–030；此前文档 025–029 为历史范围。030 不调整全库默认权限，不影响其他业务函数。仍须按迁移顺序执行，若缺前置函数整笔失败。

## 依据及验证

旧 SQL 只撤 PUBLIC，不能消除角色显式授权；Supabase 官方也要求明确撤销 anon/authenticated 的函数权限：[Database functions](https://supabase.com/docs/guides/database/functions)。本次已用默认授权模拟及实际 SET ROLE anon 调用验证，未对生产发起调用探测，不能据此断言曾被利用。

全套隔离回归 40/40、脚本和测试独立类型检查、--help、npm run build 通过；保留既有包体警告。本轮未代用户执行生产授权变更、未提交或推送。
