# MBS 维护整改计划

日期：2026-10-21。状态：批次一至三已完成本地实现与合成数据验证；未发布，未执行生产核查或迁移。批次三报告记录新增方案和发布阻断项。

## 依据与判断边界

- 依据开发宪章 v5.0、项目状态日志、本地实际入口及业务代码、Trae 的复核意见。
- 代码缺陷、生产暴露程度、已发生的经营损失分别记录。未核对生产版本和账目，不认定已经发生损失或泄露。
- 本地小程序已注册 recharge 页面，购物车余额不足时有跳转入口；后端已挂载无支付凭证校验的充值接口。这说明本地路径可达，不能证明已发布版本一致，也不能以隐藏页面替代服务端保护。
- 当前 migrations 中未找到同步 settlement_items 的触发器或函数。线上是否存在额外触发器待只读核对，禁止假定存在或直接新增重复同步。
- 手动改价是现有业务能力：当前前端允许 CEO/收银改价并限制最低价。整改保留这一能力，将权限、适用范围和价格校验落实到服务端。
- 已知技术债、开发占位和代码注释不降低保护真实数据的要求；优先级结合可达性、权限、资金影响和实际开放情况确定。

## 边界与交付规则

- 不读取、输出密钥值、完整客户资料和真实交易明细；生产核查优先使用版本标识、结构元数据及脱敏汇总。
- 不探测生产漏洞，不制造测试余额，不改写历史账目，不批量重置员工密码。
- 不擅自扩大角色权限；以现有明确业务规则为准，冲突项形成规则表后确认。
- 不把停止新增不安全充值与冻结既有余额消费混为一谈；保护已有顾客余额和正常服务。
- 本地修改、验证与材料整理按任务推进；push 由项目主人执行，生产配置、迁移和正式发布按已有授权边界办理。
- 每批只解决一个完整业务单元，更新状态日志；涉及店铺操作的变更同步公告和使用说明。

## 阶段 0：建立事实清单

目标：明确哪些代码正在运行，避免将本地风险当成已发生事故，也避免遗漏无页面入口的后端接口。

工作：
1. 只读记录本地分支、工作区未提交变更、当前提交，保护已有工作。
2. 对照 Vercel 部署提交、小程序正式/体验版本，分别记录已确认与未确认状态；单凭本地 app.json 不认定线上开放。
3. 建立接口矩阵：认证方式、允许角色、店铺范围、顾客归属、返回字段、前端调用位置。
4. 核对生产数据库列、约束、索引、触发器和函数定义；只查看结构，不查询用户明细。
5. 将充值、退款、次卡、改价、人工收款的现有规则整理为验收表。

验收：每个高风险事项有本地证据、线上状态、影响范围、处理方案；未知事项不写成已确认。

## 阶段 1：阻止无实收依据入账与敏感信息落日志

工作：
1. 服务端阻止顾客凭档位直接增加余额；前端去掉模拟支付成功承诺，明确展示当前可用充值方式。
2. 未接通真实支付前，可关闭顾客自助充值新增入账；若采用到店充值，须走有权限员工确认实收的独立流程，不能把顾客点击当实收。
3. 到店自提订单区分未付款、已付款和履约状态，不将顾客选择到店付款自动记作到账。
4. 删除原始请求体、明文密码和完整支付解密对象日志，保留请求标识、业务标识、状态和脱敏错误。
5. 生产 JWT 密钥缺失时拒绝启用认证服务；上线前只核查配置是否有效，不展示密钥内容。

验收：未经实收验证不能增加可消费余额；到店付款不自动记已收；正常既有余额消费不受影响；日志无密码和完整个人数据。

## 阶段 2：落实身份与最小权限

工作：
1. 先修复店铺设置、团购管理、客户删除等明确缺少认证或角色限制的接口。
2. 对客户列表、画像、记录、财务和导出统一实施服务端角色与数据范围校验，前端与后端使用同一规则口径。
3. 顾客身份验证形成完整方案：选定可信登录凭据，签发顾客会话，服务端从会话推导 customerId；不信任请求自行声明的身份。
4. 顾客余额、订单、次卡、评价及改签等接口检查归属，按用途返回最少字段。三端同步适配后再收紧旧接口，避免登录和个人中心整体中断。
5. 员工密码采用哈希存储；先识别旧存储格式，设计受控兼容迁移，禁止强制统一密码。新建和改密仅写哈希，旧格式逐步迁移并有结束条件。
6. 员工停用、降权、改密后可撤销会话；旧 token 不继续携带有效高权限。

验收：未登录请求被拒绝；低权限与跨店/跨顾客操作被拒绝；合法角色业务正常；旧员工账号按迁移方案可用；停用后访问失效。

## 阶段 3：资金、次卡和支付一致性

工作：
1. 服务端读取可信价格与会员配置，计算应收并验证改价角色、最低价、原因和权益归属；金额拒绝负数、非有限数和非法支付方式。
2. 余额扣减、结算、权益、次卡与业务流水使用数据库事务或受限数据库函数，实施余额充足条件和原子更新。
3. 为结算、充值、支付回调、人工确认和次卡核销建立业务幂等标识与唯一约束。
4. 次卡核销从前端单独补请求迁入服务端业务闭环，失败不能仍显示完整成功；核对旧预约完成逻辑，避免同一服务双重核销。
5. 支付回调核对交易归属、金额和币种；状态切换具备并发保护；人工收款保留独立权限与证据，不能伪造渠道到账事实。
6. 设计可恢复处理状态与持久补偿任务；已收款但权益未处理可安全重试，推荐奖励不能只依赖未等待完成的异步调用。
7. 退款核对实际支付通道，明确余额、库存、积分、次卡、优惠券和推荐奖励的返还或撤销规则。

数据库要求：先核对线上结构，新增有序 migration；在隔离 schema/项目验证完整脚本，不直接在生产做实验。历史异常先形成脱敏核对清单，不自动改账。

验收：重复请求不重复入账/扣款；并发消费不超额；失败中断后可恢复；次卡次数与日志一致；退款总额受原交易约束；正常现金、余额、微信、零元核销均通过。

## 阶段 4：报表与运营闭环

工作：
1. 先核查 settlement_items 真实来源，选定唯一明细来源，避免重复写入或按不完整数据统计。
2. 明确实收、营业额、储值充值、储值消费、赠送和退款的口径；统一门店时区及周期边界。
3. 建立每日收款、余额、次卡对账和异常处理清单，明确处理角色、时限与复核记录。
4. 发布记录包含后端提交、网页版本、小程序版本、迁移执行状态和验收结果；归档旧待办，不能删掉历史证据。
5. 在独立环境验证备份恢复，记录恢复目标与责任人；支付失败和业务处理失败提供脱敏告警。

验收：脱敏样本可从实收追溯到订单与权益；统计不受页面筛选意外截断；所有异常有处理人和关闭依据。

## 阶段 5：工程维护能力

- 为权限拒绝、重复回调、并发余额/次卡、异常恢复和退款等关键行为增加有意义的测试。
- 分页读取客户与历史记录；报表使用有界查询或数据库聚合。
- 随业务整改逐步拆分主路由、统一 API 错误处理，防止真实接口失败静默降级为 mock。
- 分模块收紧类型；不在一次修复中全仓重构或删除未确认用途的 server 代码。

## 每批验证与回退

- 按宪章执行 npm run build → npm run server:api → 浏览器/小程序相关 Network 和业务验证；发布前最后一次验证为构建。
- 资金与权限测试仅使用隔离环境和合成数据；本地后端也须确认不连接生产后才做写入测试。
- 本地验证、三端验证、生产验证分别记录；未完成的验证不得写成通过。
- 发布后验证明确的核心流程；回退不能重新开放无实收入账或绕过权限的旧路径，必要时停用该入口并保留正常业务。
