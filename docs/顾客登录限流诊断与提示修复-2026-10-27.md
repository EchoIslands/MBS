# 顾客登录限流诊断与提示修复

## 问题及范围

主人在微信订单详情验收时，用已改密的顾客0001账号首次手动点击登录即收到“尝试次数过多”。截图不足以判定密码错误或锁定原因。

1. 先检查登录客户端是否重复提交、后端限流键及数据库当前聚合状态。生产检查只读：不读取密码、手机号或原始 IP，不重置计数、不代登录。
2. 主人已在本轮确认改为正确登录不消耗失败额度；同 IP 每日最多十次密码失败，连续五次失败锁定十五分钟。区分日配额、临时锁定与并发验证占满；返回真实等待秒数，不关闭限流。
3. 核查部署代理 IP 来源，可信头缺失不得把不相关访客默默合并为 unknown；如需变更，依据托管平台文档和证据实现。
4. 验收：隔离数据库/真实 HTTP 验证成功与失败计数、限流原因及等待时间、客户端无重复请求；生产构建、后端启动、浏览器 Network 检查通过。记录仍待主人决策及线上实测事项。

## 当前代码发现

- `begin_customer_auth_attempt` 在验证密码前增加同一 IP 的 daily_attempts，成功登录不减少日累计；首次设密探测与修改密码也共享这一个配额。达到十次后，即使密码正确也不进入密码验证。
- 数据库虽返回 retry_after_seconds，后端只保留 allowed 布尔值；日配额目前固定返回86400而非距实际重置的时长。前端无法解释限流原因和恢复时间。
- 小程序 onLogin 有 loggingIn/restoringSession 防重，页面加载仅恢复凭证，不自动重复提交密码。尚不能仅凭静态代码证明本次请求只发出一次。

## 已核实证据及实现选择

- 生产只读事务检查实际列及聚合：当天唯一活跃计数为10，失败计数0，无尚未到期的临时锁；没有读取密码、手机号、原始IP或HMAC。与日配额拦截吻合，但未匹配请求IP，也不能由失败计数0反推出十次均为成功登录。旧日界为UTC，对应北京时间08:00恢复。
- 043新增独立失败日计数（北京时间自然日）及短期验证占位表；不把无法区分成功/失败的旧daily_attempts冒充新失败次数，不清空原连续失败及有效锁定。旧函数供已部署旧代码过渡，新代码只调用v2；缺迁移返回503并明确提示，不回退绕过限流。
- 每次验证先在同IP行锁下占位，已失败数+占位最多10；验证成功释放占位且不增加日失败，已核对的错误密码才增加失败。无密码首次设密探测、数据库故障及资料冲突取消占位，不伪装成功清除失败。
- 占位带随机UUID、两分钟到期，完成只能消费一次；同IP固定锁顺序防重复完成和死锁。过期完成拒绝，不颁发凭证；清理过期占位，防中断长期占满。成功不得清除较新的并发失败锁；日切只清日失败，不清有效十五分钟锁。
- 后端登录和改密共用上述机制，429带错误码、Retry-After、等待秒数、北京时间恢复时间；小程序和网页沿用服务端提示，不索要或记录密码。新增SQL由主人手动执行，维护者不操作生产计数。
