# 历史支付恢复状态修正

问题：继续历史微信结算时，仅凭没有二维码便提示支付处理中，普通草稿和查询异常也被误判；提示后仍可提交，重复遇到数据库保护。

用户确认这些是未支付历史单，之前没有生成二维码。查询接口显式区分可编辑草稿、可恢复原二维码、已有支付但二维码缺失、初始化已认领和已完成；查询失败受控拒绝，不冒充无支付单。前端对无支付记录的陈旧初始化认领发起原子恢复，恢复规则要求认领超过5分钟、单据仍待支付/失败且payments完全无记录；行锁串行化与数据库再次校验防并发。任何支付记录都不释放。恢复后在同一原单号继续结算，不删单、不生成第二结算。

新增 migration 032，为认领写入时间并安装安全 definer 的原子恢复函数。已存在031的数据库需运行更新后的 `npx tsx scripts/upgrade-checkout.ts`（幂等重跑031并安装032），随后运行发布检查。迁移本身不批量扫描/改写任何历史交易；只有员工点击“继续结算”时针对选中的单据检查并释放过期且无支付记录的claim。

本地验证：安全回归18/18、事务回归13/13、安装脚本回归4/4通过；覆盖旧claim释放、5分钟新claim保护、有payments记录时拒绝释放；构建通过（既有主包体积警告）。本地合成配置启动health200、diff检查通过。未完成浏览器Network、真实网关及历史单验收；未推送。

剩余验收：本地协议按用户提供的业务事实支持陈旧且无支付记录的历史单继续；浏览器/真实数据库迁移及微信网关尚未验收。若库中发现任何payments记录，系统继续阻断并要求对账。

最终保护边界：自动恢复仅限032之前无认领时间戳、创建超过5分钟且没有支付记录的历史单。032之后有时间戳的新认领即使等待超过5分钟，也不自动释放，防止仍在处理的慢请求随后写入映射；此类失败需独立恢复与对账。前文“超过5分钟”必须结合此限定理解。安装与部署需在暂停收银且没有旧版本请求运行时完成。
