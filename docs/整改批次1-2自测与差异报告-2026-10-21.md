## 3. 批次二：集中权限与数据范围

新增 `api/middleware/permissions.ts`，以共享 `shared/permissions.ts` 为角色规则来源，通过 `requirePermission`、`requireOwnShop`、`scopeCustomerQuery`、`requireCustomerScope` 组合执行；不在本批各路由复制角色 if-else。

| 接口/操作 | 身份与角色要求 | 数据边界 |
|---|---|---|
| `GET /api/customers` | 当前有效员工；CEO、店长、客服、发型师 | 强制当前数据库员工店铺；发型师仅返回 `served_by_stylist_ids` 包含本人 ID 的客户，先在数据库查询中筛选，再查询关联画像/到店记录。 |
| 客户详情、画像读取、会员登记记录 | 同上 | 同店；发型师必须属于该客户服务人员，不可通过换 ID 绕过列表筛选。 |
| 客户新增/删除 | CEO、客服 | 店铺由当前员工决定；请求不能指定其他店铺。删除权限按本轮项目主人明确指令允许客服。 |
| 客户更新、画像修改、会员更新 | CEO、客服 | 同店；画像和会员更新增加统一客户范围前置校验。 |
| 签发顾客登录凭证 | CEO、客服，并显式确认已核实本人 | 同店目标客户；不接受发型师、店长自行签发。 |
| `/api/financial/*` | CEO | 原报表按当前员工店铺取数；整个路由组统一认证、角色校验。 |
| `PUT /api/shops/:id` | CEO、店长 | 路径店铺必须等于当前数据库员工店铺。 |
| 本人信息 `GET /api/customers/:id/public` | 顾客本人会话 | 请求 ID 必须与已验证凭证中的顾客 ID 一致，数据库再次确认顾客及店铺；员工 token 不能冒充顾客会话。 |
| 本人次卡 `GET /api/customers/:id/packages` | 顾客本人会话 | 同上，次卡查询同时限定顾客与店铺。 |

匿名返回 401、有效身份无权限返回 403；无权读取某客户时统一返回 404，避免暴露目标客户是否存在；身份查询故障返回 503，禁止失败放行。

员工中间件改为每次读取当前员工状态、角色、店铺和密码版本。停用、调店、降权立即按数据库新状态处理；改密后旧会话失效。新增 audience/issuer/kind 与 HS256 限制，员工和顾客 token 不互通。生产缺失或不符合约束的 JWT 密钥时拒绝启动；本地缺配置采用进程级随机密钥。

## 4. 顾客身份方案与运营影响

现有代码没有可直接使用的短信校验或微信 code2session 身份链。因此本批实现的是**人工核实后签发短期登录凭证的本地待审方案**，并未接通短信或微信自动身份认证。

1. CEO/客服按门店认可的身份核实流程确认顾客本人，进入客户详情点击签发按钮，确认已核实。
2. 后端签发绑定 customerId、shopId、用途的 15 分钟有效登录凭证。员工将凭证通过已核实的本人渠道交给顾客，不公开发送。
3. 顾客用匹配的手机号和该凭证登录；手机号单独不能查余额或个人信息，也不再自动注册或借登录修改姓名。
4. H5 使用 HttpOnly、SameSite=Strict 的 Cookie，生产启用 Secure，路径 `/api`，有效期 2 小时；普通 H5 登录响应不返回 bearer token。
5. 小程序显式请求 mini 登录模式，保存独立顾客 bearer token，请求封装附带；401 清理会话，旧版仅有顾客 ID 的本地记录不能充当登录态。
6. 本人信息使用字段白名单，不返回身份证、微信标识或完整客户画像。认证响应与受保护请求添加 no-store。

重要限制与发布决策：

- 人工核实是否充分取决于门店执行，点击确认本身不证明线下身份。当前未建立核实证据与签发审计持久化。
- 登录凭证有效期内可再次换取会话，**不是一次性验证码**；目前无单顾客立即撤销机制，登出只清理当前端凭证，不使已复制的 bearer token 立即失效。
- 两小时后须重新登录，未实现刷新会话；该流程增加客服工作量，上线前由项目主人审核，并培训门店。
- H5 Cookie 按同源 `/api` 部署设计；跨站 API 不在本批支持范围，不能仅修改 CORS 就宣称兼容。
- 小程序和 H5 要与后端协同升级。旧客户端凭手机号登录将被拒绝，须先规划版本发布顺序与门店通知。
- `customer_packages` 增加店铺限制后，历史顾客与次卡店铺不一致的记录将不返回。上线前应只读核对这类数据；不能用恢复无店铺过滤来绕过权限。
- 顾客预约、订单、评价、改签等其他历史接口的完整归属审计未完成，本批不能标记为“全站权限整改完成”。

## 5. 密码平滑迁移

新增 `api/lib/password.ts`：bcrypt cost 12，旧明文通过摘要等时比较校验，首次正确登录后才条件更新为哈希，迁移完成才签发会话。

- 错密码不更新、不签发会话。更新条件包含员工 ID、旧密码值和启用状态，避免并发覆盖其他改密；条件更新未命中时重新核实当前密码。
- 迁移写入故障返回 503，不删除旧值、不签发会话；恢复后可继续用原密码登录。
- 历史短密码可迁移；超过 bcrypt 72 UTF-8 字节限制的历史密码使用带格式前缀的 SHA-256 预哈希后 bcrypt，不截断密码。新密码限定至少 6 字符且最多 72 UTF-8 字节。
- 新建员工、员工改密、本人改密只写哈希；员工列表及新增/修改响应排除 password_hash。
- 未做全员强制重置；未自动批量清理尚未登录员工的旧明文。迁移结束条件、未登录账号处理方式仍需后续运营决策。
- 旧员工 token 因格式和密码版本规则变化需重新登录，密码仍为原密码。
- **回退约束**：一旦生产有密码迁移，不能直接回退到只比较明文的老认证代码，否则已迁移员工无法登录。回退版本必须保留哈希兼容验证，也不得恢复不安全充值或匿名本人查询。

生产发布前须只读确认现有 password_hash 列可存储新格式（超长旧密码格式约 71 字符）、字段类型/长度、写入权限以及 JWT_SECRET 配置合规；本轮未查询这些生产结构或配置，也不输出任何密钥。
